# Cloud Development Policy: Projected Diataxis Output

## Scope

This report evaluates [CloudDevelopmentPolicy.md](governance/policies/CloudDevelopmentPolicy.md) and the ten local documents it links to in `software-engineering-policies/CloudDevelopment/`. It also checks for overlap with the related policy families already in `governance/policies/`.

The derived base name is `cloud-development`, removing the document-type suffix `Policy` from `CloudDevelopmentPolicy.md`.

This is an analysis only. It does not create the projected documents, change the source policy, or move any source files.

## Classification Summary

The source set contains three kinds of useful content:

- **Policy:** the cloud policy's scope; security taking precedence in cloud decisions; Terraform and new-project IaC expectations; Key Vault and secret-handling controls; personal-data and logging statements; backup and recovery expectations; the Cloud Pilot's Licence requirement; and resource-tag requirements. Some are qualified recommendations rather than absolute rules and must retain their wording.
- **Explanation:** cloud-first context, stated benefits and challenges, the policy's stated aims, and why logging, monitoring, and disaster recovery matter.
- **How-to:** source-supported actions for starting a project with the UKHO Terraform template, arranging project networking and shared modules, adding IaC scanning, and planning and exercising disaster recovery. The source does not contain a technical restore runbook.

The policy set also contains incomplete, explicitly WIP, or unresolved material. It should not be promoted to policy without decisions from the relevant owners.

## Existing Policy Overlap

- **Containers:** use the current containers policy family. The cloud-specific container source is effectively a pointer and an empty heading.
- **Pipeline and security scanning:** Secure Development should own the cross-cutting minimum for security scanning. IaC, SAST, container, and software-composition analysis (SCA) scan tasks are available as Azure DevOps YAML tasks in the [UKHO pipeline scan-task documentation](https://github.com/UKHO/ukho-azure-pipeline-scan-task/blob/main/README.md); implement the task wherever repository content relevant to that scan type exists. Keep pipeline-specific implementation guidance in the Pipeline Policy. The recommendation to consider DAST where appropriate should be in Secure Development, not the Pipeline Policy. Reconcile timing, thresholds, and exception authority against the specialized cloud and container guidance.
- **Logging and observability:** existing policies specify Elastic, logging fields and handling, APM, and SolarWinds. The cloud sources should link to them. The statement allowing pseudonymized PII in logs conflicts with the Logging Policy's direction not to store personal information and requires an explicit decision.
- **Recovery and service requirements:** link to the NFR policy for discovering and demonstrating service requirements. Keep cloud-specific backup, restoration, and data/metadata consistency content only where it adds a distinct cloud recovery requirement.
- **Identity and access:** the existing sources and linked account/security material may be relevant, but the `Users.md` proposals are WIP and do not establish approved cloud identity rules.

## Decisions Needed Before Generation

1. Confirm whether the source set is an approved policy or remains a draft. The root document labels itself version `0.1` with a blank approval status.
2. Confirm the applicability and force of Terraform use, the deployment template, DDC networking, module reuse, and scan-failure-at-risk-appetite requirements.
3. Resolve the scanning differences before consolidating requirements:
   - **Tooling (resolved):** Snyk is the designated UKHO tool for all scan types discussed here: infrastructure-as-code (IaC), static application security testing (SAST), software-composition/dependency analysis, and container scanning. `General.md` identifies Snyk for IaC and requires the provided pipeline task in infrastructure repositories; `Deployment.md` describes it as preferred and connected to GitHub for SAST and software-composition analysis; the pipeline policy calls the UKHO Snyk task highly recommended; and secure development requires the designated dependency and SAST tools without naming them. Align these varying descriptions to the resolved designation. This settles tool identity, but not scan timing, thresholds, or exception handling below.
   - **Coverage (resolved):** Secure Development should own the cross-cutting minimum for scanning. IaC, SAST, container, and software-composition analysis (SCA) scan tasks are available as Azure DevOps YAML tasks; see the [UKHO pipeline scan-task documentation](https://github.com/UKHO/ukho-azure-pipeline-scan-task/blob/main/README.md). Implement a task wherever repository content relevant to that scan type exists. The cloud source's IaC-specific requirement and the container policy's image-specific requirements remain specialized controls that should align with, not replace, this minimum. The recommendation to consider DAST where appropriate belongs in Secure Development, not the Pipeline Policy; the pipeline policy should describe how applicable checks are implemented in pipelines.
   - **Timing and gate:** `Deployment.md` says SAST runs when a PR is raised and regularly, strongly encourages adding SAST to the pipeline, and advises scanning a built container before it is pushed to a registry. `General.md` requires an IaC scan task in infrastructure repositories but does not specify its execution point. Pipeline policy describes scans as part of pipeline design without a precise stage. Secure development requires dependency scanning before production release but does not specify PR timing. By contrast, container policy requires image scanning before release into an environment and says High-or-higher findings stop the pipeline. Agree the minimum event/stage for each scan rather than assuming these timing statements are equivalent.
   - **Thresholds and disposition:** the cloud sources say pipelines should fail at a level matching the project's risk appetite and that vulnerabilities exceeding it should not reach cloud environments. Secure development says teams set acceptable dependency and SAST thresholds, requires evidence that a breached threshold blocks production release, and requires risk-owner approval for a decision to release despite a known dependency vulnerability. The container policy supplies a concrete High-or-higher stop threshold and allows seeking Security team or Lead Developer advice about mitigation or suppression if no fix is found. It does not specify that this advice itself authorizes an exception. `Deployment.md` discusses false positives and seeking advice on mitigation/suppression, but does not define an approval authority or documented exception record. Decide whether cloud IaC uses project-defined risk appetite or a common severity threshold, who can approve an exception, and what evidence or review record is required; preserve the container-specific threshold unless its owning policy changes it.
4. Resolve the differences between the cloud logging guidance and the existing logging policies:
   - **Scope and force (human-reviewed and agreed):** the Software Engineering Logging Policy applies to services developed and supported by Software Engineering and defines concrete requirements and assurance practices. `LoggingAndMonitoring.md` is broader cloud-deployment guidance, mostly phrased as recommendations (“consider”, “should”), and points readers to the Logging Policy and the separate security-focused SharePoint policy. Link to the existing Logging Policy rather than duplicate its requirements; retain only cloud-specific additions where a specific gap is identified.
   - **PII and sensitive data:** `DataUse.md` says PII should be minimized and/or anonymized in system logs, and that PII required in logs should be pseudonymized. The Logging Policy advises avoiding customer information and says personal information, including customer names, addresses, and email addresses, should not be stored in logs. These are not equivalent: pseudonymization still retains a link to the individual, while the Logging Policy's wording disallows storing personal information. Confirm whether logging personal data is prohibited, or whether a narrowly defined exception is permitted and under what authority and safeguards. Do not present pseudonymization as satisfying the current Logging Policy without that decision.
   - **Platform and implementation (resolved):** Elastic is the UKHO standard platform for logging and observability; on-premise Elastic no longer exists. Some legacy solutions use LogShipper to direct logs from on-premise systems to Elastic in the cloud. The cloud guidance's `UKHO.Logging.EventHubLogProvider` reference and its general recommendation to use centralized Elasticsearch are out of date. The [Logging Policy](governance/policies/logging.md) is correct to prefer `UKHO.Logging.Serilog` over the legacy `UKHO.Logging.EventHubLoggingProvider`; its wording `UKHO.EventHubLogging` is a misnaming of that same provider. Link to the Logging Policy rather than duplicating its platform, ingestion, and migration requirements, and retain additional cloud logging information only where it addresses a specific gap.
   - **Logging detail and assurance (human-reviewed and agreed):** the Logging Policy specifies required fields, categories and expected production levels, index naming, ingestion checks, Definition of Ready/Done expectations, tests, handover assurance, and load-test logging. The cloud guidance does not define these details; it recommends agreeing formats/levels, controlling access, and avoiding unnecessary sensitive data. Link to the policy and its reference rather than duplicating these details unless a cloud-specific gap is identified.
   - **Monitoring and ownership:** the cloud source recommends Elastic APM, correlation IDs, dashboards, alerts, balancing alert noise, and SolarWinds for Business Central. The separate Observability Policy calls Elastic APM the standard for application metrics/observability and SolarWinds the standard for endpoint/host monitoring and extended-support callouts; it also allows relevant service-based monitoring and requires API keys to be held in Key Vault. Confirm which cloud recommendations are still current, distinguish logging from monitoring/observability, and link to the owning policy rather than restating standards. The cloud source's separate security-focused SharePoint policy is outside this repository review and may contain additional controls to reconcile.
5. Confirm the intended UK data-sovereignty rule; the relevant source section contains only an unresolved marker. Also clarify the scope of “Applied policies” for tagging.
6. Confirm the mandatory training audience and its prerequisite relationship to elevated account access.
7. Decide whether the disaster-recovery statements are requirements or recommendations, and preserve SLA dependence and agreed recovery limits when doing so.
8. Resolve the WIP user-authentication proposals with the relevant identity and security owners before including any of them.

## Link and Migration Notes

- The cloud policy's local links to the ten source documents are valid from its current location. The source files link back to the root policy; those return links need updating if the source material is migrated.
- The root policy's relative `CodeReviewPolicy.md` and `ContainerPolicy.md` links do not resolve from `governance/policies/`. Similarly named historical files are under `governance/policies/Processed/`; the current policy families are `code-review.md` and `containers.md`.
- `Deployment.md` links to `/software-engineering-policies/Containers/`, which does not match the current `CloudDevelopment/Containers.md` path.
- `DataUse.md` embeds an image using a path relative to its current directory. Preserve that image or update its link if the content moves.
- The sources rely on external GitHub, SharePoint/Nautilus, and ICO material. Assume these links are valid as specified and access to the material is controlled by the external destination.

## Recommendation

Proceed with the three projected documents above only after resolving the decisions that affect normative meaning. Keep WIP material out of the generated requirements, and use links to the existing governance policies wherever those policies already own the subject. No source file should be moved as part of this analysis-only deliverable.
