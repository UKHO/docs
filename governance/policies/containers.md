# Container Policy

This policy defines the secure development and deployment of containers. For context, see the [explanation](containers-explanation.md). For practical guidance, see the [how-to](containers-how-to.md).

## Policy

- Architects may consider containers as one option in their toolbox.
- When considering containers, teams should consider why they want to use them and who will inherit the environments, including whether they have the expertise to manage the hosting environment.
- Containers may be used in development and test environments without APF review.
- In the Software Engineering department, deployment of containers into live environments must be approved by the Head of Software Engineering in conjunction with the Principal and Lead Software Engineers, until agreement is reached via the APF forum.
- Containers are a core software and test engineering tool.
- All teams using containers should adopt the practices in this policy.
- The Lead Software Engineer for each team is responsible for ensuring that this policy is followed.

## Image and Dockerfile practices

- Where a container needs secrets or passwords, these should be injected into the container through environment variables defined in the Dockerfile and encrypted at a minimum.
- Dockerfiles should be linted to detect issues and vulnerabilities.
- Teams should aim to use minimal dependencies, such as a [distroless container base](https://github.com/GoogleContainerTools/distroless).
- Teams should avoid defining unnecessary privileges and avoid running containers as root. They are advised to create a non-root user with access only to the service code. For .NET 8.0, a non-root user is [provided by the platform](https://learn.microsoft.com/en-us/dotnet/core/whats-new/dotnet-8/containers#non-root-user).
- Teams should ensure there is a well-established process for updating dependencies.
- Where both suitable and possible, teams should use [multi-stage builds](https://docs.docker.com/build/building/multi-stage).
- The selected container image should be the leanest image that meets the application's needs, with only the dependencies required to run it. When selecting an image, teams should start with the Alpine version and move to a fuller version only if too many Dockerfile modifications are needed.
- New images are recommended to be based on the UK Hydrographic Office's [approved DockerHub images](https://hub.docker.com/u/ukhydrographicoffice). The Dockerfiles for these images are in the [UKHO dockerimages repository](https://github.com/UKHO/dockerimages).

## Deployment practices

### Must do

- Where applicable at deployment, secrets must be stored using Azure KeyVault, AWS Secrets Manager, etc.
- CPU and memory resources, limits, and requests must be defined for container deployments.
- Container deployments and their deployment environments must be configured using infrastructure as code.
- Deployments must include a means to monitor container health. For example, Kubernetes deployments should configure readiness and liveness probes.
- Environments above Dev must enforce HTTPS and enable HTTP-to-HTTPS redirects.
- Logs generated by containers must be consumed.
- Access to the underlying infrastructure running container images must be blocked in all environments above Dev.
- Container images must be scanned by a vulnerability scanning tool. Before releasing a container into an environment, teams should perform a scan. High or higher findings should not be allowed; findings at this level should stop the pipeline and be investigated for possible upgrades or fixes.
- Container deployments must not become a persistent data store or silo.
- If no fixes are found for a high or higher vulnerability and the team believes it will not affect its system, it may ask the Security team or Lead Developers for advice on mitigation or suppression.

### Should do

- Microservices and containers should communicate only with the services and ports they need.
- Access Policies and Network Security Groups should be applied.
- Container deployments should be isolated using Namespaces.
- A monitoring solution should be in place for deployed containers. Examples include ELK (.NET), EFK (Java), Grafana, and Prometheus.
- Automated deployments should be used when container image versions are incremented within the container registry.

### Could do

- Native Visual Studio support for Docker could be used for development and testing.
- Docker Compose could be used to stub other dependencies used by the container.

## Exclusions

This policy does not cover:

- Docker Desktop. It is a licensed product; approval and licence acquisition should follow the standard UKHO policy.
- Kubernetes. This policy focuses on containers, not their hosting environment.
