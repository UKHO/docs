# How to Apply Container Security Guidance

This how-to applies the [Container Policy](containers.md) when building and deploying a container. The policy remains the authoritative source for requirements.

## Select a container image

1. Select the leanest image that contains the dependencies required to run the application, as the policy recommends.
2. The policy recommends starting with the Alpine version. Move to a fuller version only if Alpine would require too many Dockerfile modifications.

## Configure user access

1. As advised by the policy, create a non-root user for the container.
2. Give that user access only to the service code.

For .NET 8.0, a non-root user is [provided by the platform](https://learn.microsoft.com/en-us/dotnet/core/whats-new/dotnet-8/containers#non-root-user).

## Scan before release

1. Before releasing a container into an environment, run a vulnerability scan with a tool of your choice.
2. Do not allow high or higher findings. Findings at this level should stop the pipeline.
3. Investigate findings for possible upgrades or fixes.
4. If no fixes are found and you believe a finding will not affect your system, ask the Security team or your Lead Developers for advice on mitigation or suppression.

## Apply Dockerfile practices

The policy recommends the following Dockerfile practices:

- Where a container needs secrets or passwords, they should be injected through environment variables defined in the Dockerfile and encrypted at a minimum.
- Dockerfiles should be linted to detect issues and vulnerabilities.
- Aim to use minimal dependencies, such as a [distroless container base](https://github.com/GoogleContainerTools/distroless).
- Avoid unnecessary privileges and running as root.
- Ensure there is a well-established process for updating dependencies.
- Where both suitable and possible, use [multi-stage builds](https://docs.docker.com/build/building/multi-stage).
- New images are recommended to be based on the UK Hydrographic Office's [approved DockerHub images](https://hub.docker.com/u/ukhydrographicoffice). Their Dockerfiles are in the [UKHO dockerimages repository](https://github.com/UKHO/dockerimages).

Docker's guidance for [writing Dockerfiles](https://docs.docker.com/develop/develop-images/dockerfile_best-practices/), [developing with Docker](https://docs.docker.com/develop/dev-best-practices/), and [secure development with Docker](https://docs.docker.com/develop/security-best-practices/) is also available. The policy's listed practices take precedence over that general guidance.

## Configure the deployment

### Must do

- Where applicable at deployment, store secrets using Azure KeyVault, AWS Secrets Manager, etc.
- Define CPU and memory resources, limits, and requests for the container deployment.
- Configure the container deployment and its environment using infrastructure as code.
- Include a means to monitor container health. For example, for Kubernetes, configure readiness and liveness probes.
- In environments above Dev, enforce HTTPS and enable HTTP-to-HTTPS redirects.
- Ensure logs generated by containers are consumed.
- Block access to the underlying infrastructure running the container images in all environments above Dev.
- Ensure the deployment does not turn the container into a persistent data store or silo.

### Should do

- Limit microservice and container communication to the services and ports needed.
- Apply Access Policies and Network Security Groups.
- Isolate container deployments using Namespaces.
- Put a monitoring solution in place for deployed containers. Examples include ELK (.NET), EFK (Java), Grafana, and Prometheus.
- Use automated deployments when container image versions are incremented within the container registry.

### Could do

- Use native Visual Studio support for Docker during development and testing.
- Use Docker Compose to stub other dependencies used by the container.

For additional Dockerfile practices, see the [Sysdig guide](https://sysdig.com/blog/dockerfile-best-practices/).
